# 测试验收清单

## 1. 文档目的

本文档用于规定每次开发后的基本测试流程。后续测试会话应优先阅读本文档，并结合 `PRODUCT_REQUIREMENTS.md`、`API_CONTRACT.md` 和 `DB_SCHEMA.md` 验收功能是否符合当前项目约定。

## 2. 测试前准备

1. 确认当前项目目录为项目根目录。
2. 确认没有无关服务占用当前端口，默认端口为 3000。
3. 如需全新数据测试，可先备份现有 `data/database.sqlite` 和 uploads 文件夹，再使用干净数据环境。
4. 不要删除用户已有数据，除非测试任务明确要求。

## 3. 环境测试

每次开发后至少检查：

1. `npm install` 是否成功。
2. `npm start` 是否成功。
3. 本地服务是否正常启动。
4. 控制台是否输出访问地址。
5. 打开 `http://localhost:3000/submit` 是否能看到客户提交页。
6. 打开 `http://localhost:3000/admin/login` 是否能看到后台登录页。
7. 首次启动时是否能自动创建 `data/` 和 `uploads/` 目录。
8. SQLite 数据库初始化是否正常。

## 4. 客户提交测试

### 4.1 页面打开

1. 打开 `/submit`。
2. 页面标题和主标题应显示客户需求提交。
3. 表单字段应完整显示。
4. 上传材料字段应支持多文件选择。

### 4.2 必填项校验

需要分别测试以下必填项为空时的表现：

1. 姓名或昵称为空。
2. 联系方式为空。
3. 任务类型未选择。
4. 截止时间为空。
5. 具体需求为空。

预期结果：

1. 前端或后端应阻止提交。
2. 不应创建无效订单。
3. 不应留下无效上传文件。

### 4.3 正常填写需求

填写一条完整需求：

1. 姓名或昵称。
2. 联系方式。
3. 任务类型。
4. 截止时间。
5. 具体需求。
6. 附加备注。

预期结果：

1. 提交成功。
2. 页面跳转到提交成功详情页。
3. 成功页显示订单编号。
4. 订单编号格式应类似 `DD20260707001`。

### 4.4 多文件上传

测试上传多个支持格式文件，例如：

1. PDF。
2. DOCX。
3. JPG 或 PNG。

预期结果：

1. 多个文件均上传成功。
2. 文件保存到 uploads 目录。
3. 数据库 `files` 表写入多条文件记录。
4. 后台详情页能显示所有文件。

### 4.5 不支持格式上传

测试上传不支持格式，例如 `.exe` 或无扩展名文件。

预期结果：

1. 前端或后端拒绝上传。
2. 页面显示不支持格式提示。
3. 不应创建订单。
4. 不应保留不支持格式文件。

### 4.6 超大文件上传

测试上传单个超过 100MB 的文件。

预期结果：

1. 前端或后端拒绝上传。
2. 页面显示文件超过 100MB 的提示。
3. 不应创建订单。
4. 不应保留超大文件。

### 4.7 数据写入检查

提交成功后检查：

1. `orders` 表新增记录。
2. `order_no` 唯一且格式正确。
3. `status` 默认为 `未处理`。
4. `internal_note` 当前为空字符串或空值。
5. `created_at` 和 `updated_at` 已写入。
6. 上传文件对应 `files` 表记录已写入。

### 4.8 V1.2.1 提交成功详情页测试

正常提交一条需求后继续检查：

1. 提交成功后应跳转到 `/submit-success?orderNo=订单号`。
2. 成功页应重点展示订单号，并提示客户保存订单号。
3. 成功页应展示可获得的核心信息：任务类型、联系方式、截止时间、提交时间、当前状态。
4. 本次提交信息可从 `sessionStorage` 读取时，当前状态应显示为 `未处理`，不应展示后台内部备注或管理员专用信息。
5. 刷新成功页不应报错；如果 `sessionStorage` 不存在，页面至少应展示 URL 中的订单号和兜底提示。
6. `sessionStorage` 不存在或订单号异常时，当前状态不应默认显示 `未处理`，应显示无法确认类提示。
7. 点击“继续提交新需求”应返回 `/submit`，并可再次填写提交。
8. 打开后台列表应能看到刚提交的新订单。
9. 后台 V1.1 的搜索、筛选、分页、排序、状态标签和截止提醒不应出现明显异常。

## 5. 后台登录测试

### 5.1 打开登录页

1. 打开 `/admin/login`。
2. 页面应显示账号和密码输入框。
3. 页面应有返回提交页入口。

### 5.2 正确账号登录

使用默认账号登录：

- 账号：admin
- 密码：admin123

预期结果：

1. 登录成功。
2. 跳转到 `/admin`。
3. 能看到后台订单列表页面。

如果测试环境使用环境变量覆盖账号密码，应以当前环境变量为准。

### 5.3 错误账号登录

使用错误账号或密码登录。

预期结果：

1. 登录失败。
2. 页面显示账号或密码不正确。
3. 不应进入后台列表。

### 5.4 退出登录

1. 登录后台。
2. 点击退出登录或访问 `/admin/logout`。

预期结果：

1. 跳转到 `/admin/login`。
2. session 被销毁。
3. 再访问 `/admin` 应回到登录页。

### 5.5 未登录访问保护

未登录状态下测试：

1. 访问 `/admin`。
2. 访问 `/admin/orders/:id`。
3. 访问 `/api/admin/orders`。

预期结果：

1. HTML 页面访问应跳转 `/admin/login`。
2. `/api/` 接口访问应返回 401 JSON。

## 6. 后台列表测试

登录后台后测试：

1. 能看到订单列表。
2. 最新订单靠前。
3. 订单编号显示正确。
4. 客户姓名显示正确。
5. 联系方式显示正确。
6. 任务类型显示正确。
7. 截止时间显示正确。
8. 状态显示正确。
9. 点击刷新按钮可以重新加载列表。
10. 点击查看可以进入订单详情。
11. 无订单时显示空状态。

### 6.1 V1.1 后台列表增强测试

登录后台后继续测试：

1. 默认进入 `/admin` 时按提交时间倒序显示，最新订单靠前。
2. 关键词搜索可匹配订单编号、客户姓名、联系方式、具体需求。
3. 状态筛选可分别筛选未处理、处理中、已完成、已取消。
4. 任务类型筛选可分别筛选课设报告、实验报告、PPT制作、代码作业、论文/文档、其他。
5. 关键词、状态、任务类型可以组合筛选，筛选后表单保留当前条件。
6. 无匹配结果时显示“暂无匹配订单”。
7. 分页显示总订单数、当前页码、总页数，上一页和下一页状态正确。
8. 每页 10 / 20 / 50 条切换正常，并保留当前搜索和筛选条件。
9. 排序支持最新提交优先、最早提交优先、截止时间最近优先、截止时间最晚优先。
10. 状态在列表页和详情页显示为颜色标签，且保留中文状态文字。
11. 未完成且未取消的订单应按截止时间显示已逾期、今日截止、3天内截止或普通状态。
12. 已完成和已取消订单不显示紧急截止提醒。
13. 点击查看订单详情、文件下载、状态修改和内部备注保存仍正常。

## 7. 订单详情测试

进入订单详情后测试：

1. 需求信息完整显示。
2. 订单编号显示正确。
3. 客户姓名显示正确。
4. 联系方式显示正确。
5. 任务类型显示正确。
6. 截止时间显示正确。
7. 提交时间显示正确。
8. 具体需求完整显示，换行应尽量保留。
9. 附加备注完整显示；为空时显示无。
10. 上传文件列表显示。
11. 没有上传文件时显示未上传文件。
12. 文件可以下载。
13. 状态可以修改。
14. 内部备注可以修改。
15. 保存后刷新页面，状态和内部备注仍存在。
16. 返回列表链接可用。
17. 退出登录链接可用。

## 8. 文件安全测试

每次涉及上传、下载或文件管理改动后必须测试：

1. 上传文件不覆盖已有文件。
2. 存储文件名应为时间戳加随机字符串形式。
3. 不支持格式被拒绝。
4. 超过 100MB 的文件被拒绝。
5. 下载文件名尽量保持原始文件名。
6. 中文文件名下载应尽量正常。
7. 未登录不能下载文件。
8. 数据库文件不暴露给前端。
9. uploads 目录不应作为静态目录直接公开。
10. 文件记录存在但磁盘文件缺失时，应返回明确 404。

## 9. 回归测试

新功能完成后，旧功能不能失效。至少检查：

1. 后台登录不能失效。
2. 客户提交不能失效。
3. 文件上传不能失效。
4. 文件下载不能失效。
5. 数据库保存不能失效。
6. 订单状态修改不能失效。
7. 内部备注保存不能失效。
8. 未登录后台保护不能失效。
9. 默认路由 `/` 跳转 `/submit` 不能失效。
10. 现有页面路径不能被改变。

## 10. 自动化冒烟测试

当前项目已有 `scripts/smoke-test.py`，用于通过浏览器自动执行一条基础流程：

1. 打开提交页。
2. 填写需求。
3. 上传 PDF 和 JPG 测试文件。
4. 提交订单。
5. 登录后台。
6. 查看订单。
7. 下载文件。
8. 修改状态和内部备注。
9. 退出登录并验证后台保护。

运行该脚本前需要先启动服务：

```bash
npm start
```

自动化测试不能替代完整手工测试。涉及新功能、数据库变更、文件管理或安全规则时，仍需按本文档做对应专项测试。

## 12. 验收结论标准

建议进入下一阶段的最低标准：

1. `npm install` 和 `npm start` 可正常执行。
2. 客户提交流程可正常完成。
3. 后台登录、列表、详情、下载、状态修改和内部备注保存可正常完成。
4. 数据库初始化正常。
5. 文件上传下载正常。
6. 未登录后台保护正常。
7. 本次改动没有破坏已有路径和接口。
8. 文档已同步更新。
