# 后续开发计划

## 1. 文档目的

本文档用于统一后续开发节奏和版本规划边界。后续 Codex 开发会话应先阅读本文档，再结合 `PRODUCT_REQUIREMENTS.md`、`API_CONTRACT.md`、`DB_SCHEMA.md` 和 `TEST_CHECKLIST.md` 判断是否可以实施。

本文档只维护当前正式版本和下一版本预期，不再维护多版本长期路线图。

## 2. 当前规划规则

1. 项目不再维护多版本长期路线图。
2. 当前正式版本之后，只规划一个下一版本。
3. 下一版本完成、验收、发布后，再重新评估新的下一版本。
4. 未进入下一版本的想法只作为“暂不纳入当前版本”的说明，不提前写成确定版本计划。
5. 不再提前维护 V1.4、V2.0 等详细路线，以减少业务方向变化导致的反复文档修改。

## 3. 当前正式版本

当前正式版本：V1.2.3 客户补充资料上传版

状态：已通过测试验收，并已正式发布到 GitHub。

V1.2.3 已完成内容：

1. 新增客户补充资料上传页：`/supplement-upload` 和 `/supplement-upload.html`。
2. 新增客户补充资料上传接口：`POST /api/customer/orders/supplements`。
3. 客户通过“订单号 + 联系方式”验证后，可以为原订单补充上传资料。
4. 客户可以提交补充说明、补充文件，或补充说明 + 多个补充文件。
5. 新增数据库表：`order_supplements` 和 `order_supplement_files`。
6. 后台订单详情页新增“客户补充资料”区域，按补充批次展示补充时间、补充说明、补充文件列表和下载入口。
7. 原始上传文件和补充上传文件分区展示，不混在一起。
8. `/order-query` 查询成功后增加“补充上传资料”入口。
9. `/submit-success` 增加补充上传入口。
10. 未实现客户登录、聊天系统、通知系统、客户可见进度备注、文件删除、文件分类和文件在线预览。

6. 无 `sessionStorage` 或异常订单号时页面不崩溃、不空白。
7. 未新增客户订单查询、客户登录、补充资料上传或客户可见进度备注。

### V1.2.2 客户订单查询功能

1. 新增客户订单查询页：`/order-query` 和 `/order-query.html`。
2. 新增客户订单查询接口：`POST /api/customer/orders/query`。
3. 客户通过“订单号 + 联系方式”查询本人订单基础状态。
4. 查询成功后展示订单号、任务类型、联系方式、截止时间、提交时间、当前状态、需求描述摘要和文件数量。

8. 客户查询结果不展示后台内部备注、数据库内部 ID、服务器文件路径、真实存储文件名或下载地址。
9. 未开放客户修改订单能力。
10. 未实现客户登录、短信验证码、邮件通知或客户可见进度备注。

## 5. 下一版本预期：V1.3 管理员成品上传与客户下载功能

### 5.1 背景

原先考虑过将文件在线预览、文件删除、文件分类和补充文件进一步管理作为下一步方向。但在当前业务闭环中，更有价值的是让管理员可以交付成品文件，并让客户在查询订单后下载属于自己订单的成品文件。

因此，当前下一版本预期调整为：V1.3 管理员成品上传与客户下载功能。

### 5.2 业务闭环

```text
客户提交需求
→ 客户补充资料
→ 管理员处理订单
→ 管理员上传成品文件
→ 客户查询订单
→ 客户下载成品文件
```

### 5.3 建议范围

1. 管理员在后台订单详情页上传成品文件。
2. 管理员可以填写交付说明。
3. 成品文件与原订单关联。
4. 客户通过 `/order-query` 输入订单号 + 联系方式查询订单后，如果已有成品交付，可以看到交付信息。
5. 客户可以下载自己订单的成品文件。
6. 客户不能下载原始上传资料。
7. 客户不能下载客户补充资料。
8. 客户不能看到后台内部备注。
9. 客户不能看到数据库内部 ID、服务器文件路径、真实存储文件名。
10. 订单状态仍由管理员手动修改，不自动改为“已完成”。

### 5.4 暂不纳入范围

1. 客户登录。
2. 支付。
3. 聊天。
4. 通知。
5. 文件在线预览。
6. 文件删除。
7. 文件分类。
8. 返修流程。
9. 自动修改订单状态。
10. 统计导出。
11. 正式生产部署。

### 5.5 实施注意事项

1. 本节只是下一版本规划，不表示 V1.3 已经实现、验收或发布。
2. V1.3 如需新增接口，应在功能实现时同步更新 `API_CONTRACT.md`，不要提前把未实现接口写入当前接口契约。
3. V1.3 如需新增数据库表或字段，应在功能实现时同步更新 `DB_SCHEMA.md`，不要提前把未实现结构写入当前数据库结构。
4. 客户下载成品文件时，必须继续校验订单号和联系方式，不能只凭文件 ID 或订单 ID 下载。
5. 客户侧响应不得泄露后台内部备注、数据库内部 ID、服务器文件路径或真实存储文件名。

## 6. 后续开发会话工作规则

每个后续开发会话开始前应先阅读：

1. `PRODUCT_REQUIREMENTS.md`
2. `API_CONTRACT.md`
3. `DB_SCHEMA.md`
4. `DEV_PLAN.md`
5. `TEST_CHECKLIST.md`

开发前需要确认：

1. 本次功能是否属于当前下一版本预期。
2. 是否需要改接口。
3. 是否需要改数据库。
4. 是否会影响旧功能。
5. 需要执行哪些测试。

开发完成后需要确认：

1. 文档是否同步更新。
2. 原有客户提交流程是否可用。
3. 原有客户订单查询和补充上传流程是否可用。
4. 原有后台登录和管理流程是否可用。
5. 上传和下载是否可用。
6. 数据库初始化是否正常。
